Wo steckt der Schlüssel?

Das eigene Programm untersuchen, sein Verhalten festhalten und feste Mengen von Werten mit enum benennen.

1. Eine Objektart im Programm suchen

Stellen Sie sich vor, Sie sollen dem Tresorraub eine neue Art von Gegenstand hinzufügen. Dazu müssen Sie wissen, an welchen Stellen das Programm die vorhandenen Arten behandelt. Suchen Sie in tresorraub.c alle Stellen, an denen der Schlüssel vorkommt. Ihr Editor kann nach chluessel suchen; damit finden Sie Schluessel und schluessel.

Notieren Sie für jede Stelle die Funktion oder Struktur und was dort mit dem Schlüssel geschieht. Machen Sie dasselbe für die Tür.

Selbstkontrolle: Die Stellen im Startmaterial

Der Schlüssel steckt an zehn Stellen: in den Feldern schluessel und schluessel_liegt der Struktur Spielstand und in neun Funktionen:

  • startzustand legt fest, wo der Schlüssel zu Beginn liegt.
  • gegenstand_auf liefert den Namen "Schluessel", wenn die Figur auf seinem Feld steht. Daraus entsteht in der Statuszeile „Hier liegt: Schluessel“.
  • feldzeichen liefert für die Textausgabe das Zeichen k. spielfeld_ausgeben erklärt dieses Zeichen in der Legende unter dem Spielfeld.
  • vom_feld_nehmen merkt sich beim Aufnehmen, dass der Schlüssel nicht mehr auf dem Feld liegt; auf_feld_legen legt ihn beim Ablegen wieder hin.
  • handeln sucht ihn im Inventar, um die Tür zu öffnen.
  • feld_zeichnen zeichnet sein Piktogramm auf dem Spielfeld, zeichne im Inventar unter dem Spielfeld.

Die Tür steckt im Spielstand, in startzustand, feldzeichen, spielfeld_ausgeben, figur_bewegen, handeln, feld_frei und feld_zeichnen. Haben Sie mit Ihrer eigenen Datei gearbeitet, sehen die Namen anders aus, das Bild aber vermutlich ähnlich.

Überlegen Sie nun: Eine zweite Münze soll ins Spiel. Sie verhält sich genau wie die erste. Was müssten Sie im bisherigen Programm alles ändern? Und was, wenn stattdessen eine Geheimtür dazukommt, die ohne Schlüssel aufgeht?

Selbstkontrolle: Gedankenexperiment

Für die zweite Münze bräuchte der Spielstand zwei weitere Felder, und jede der Stellen von oben bräuchte einen weiteren Fall. Das Inventar speichert Namen; zwei Münzen hätten denselben Namen, und die Regel „jeder Gegenstand höchstens einmal“ würde die zweite ablehnen. Für die Geheimtür wären es fast dieselben Stellen wie für die Tür. Jede neue Art und jedes weitere Objekt verlangt Änderungen quer durch das Programm, und jede vergessene Stelle ist ein Fehler. Genau das soll sich in diesem Kapitel ändern.

2. Das Verhalten festhalten

Sie werden Ihr Spiel in diesem Kapitel stark umbauen. Danach soll es sich genauso verhalten wie vorher. Wie können Sie das prüfen, ohne jedes Mal das ganze Spiel durchzuspielen?

Dafür liegt im Startmaterial der Vergleichslauf ablauf.c. Er startet Ihr Spiel über dieselben Funktionen wie das Gerüst, drückt eine feste Folge von 54 Tasten und gibt nach jeder Taste die Meldungen, die Statuszeile und eine Prüfsumme des gezeichneten Bildes aus. Ändert sich auch nur ein Pixel, ändert sich die Prüfsumme.

  1. Bauen Sie den Vergleichslauf mit make ablauf und speichern Sie seine Ausgabe: ./ablauf > vorher.txt. Diese Datei bewahren Sie bis zum Ende des Kapitels auf.
  2. Lesen Sie vorher.txt. Welche Spielsituationen kommen vor?
  3. Ändern Sie probeweise eine Meldung in tresorraub.c, etwa „Hier gibt es nichts zu tun.“, bauen Sie neu und vergleichen Sie mit ./ablauf > nachher.txt und diff vorher.txt nachher.txt. Machen Sie die Änderung danach rückgängig.
Selbstkontrolle: Der Vergleichslauf

Die Folge enthält eine Wand und eine verschlossene Tür als Hindernis, die Tür ohne Schlüssel, Aufnehmen, Ablegen und Wiederaufnehmen des Schlüssels, das Öffnen der Tür, Münze und Beute, Ablegen von zwei Gegenständen, ein leeres Inventar und eine Taste ohne Bedeutung. Nach der geänderten Meldung zeigt diff genau die Zeilen mit dieser Meldung. Nach dem Zurücksetzen ist die Ausgabe von diff leer.

Ein solcher Test beschreibt nicht, wie das Spiel sein soll, sondern wie es ist. Er ersetzt keine Tests, die Regeln prüfen. Für einen Umbau ist er trotzdem sehr nützlich: Jede Abweichung ist entweder ein Fehler oder eine Änderung, die Sie erklären können.

3. Feste Mengen von Werten: enum

Im Startmaterial stehen die Ergebnisse von inventar_aufnehmen als #define: AUFGENOMMEN, SCHON_VORHANDEN, INVENTAR_VOLL und zwei negative Fehler. Die Funktion liefert aber ein int. Dass nur diese fünf Werte gemeint sind, steht nirgends im Code.

Für eine feste Menge benannter Werte gibt es in C den Aufzählungstyp enum:

typedef enum {
    ROT,          /* 0 */
    GELB,         /* 1 */
    GRUEN         /* 2 */
} Ampel;

Ampel a = GELB;

Jeder Name ist eine ganzzahlige Konstante. Ohne Angabe beginnt die Zählung bei 0 und steigt um 1. Mit = wert legen Sie einen Wert selbst fest; die folgenden Namen zählen von dort weiter. Probieren Sie in text_ausgeben aus und notieren Sie vorher Ihre Erwartung:

  1. Geben Sie ROT, GELB und GRUEN mit %d aus.
  2. Ergänzen Sie die Aufzählung so: AUS = -1, ROT, GELB, GRUEN. Welche Werte haben die Namen jetzt?
  3. Schreiben Sie eine Funktion mit einem switch über eine Ampel, die zu jedem Wert einen Text liefert, und lassen Sie einen case weg. Was meldet der Compiler mit -Wall?
  4. Weisen Sie a = 7; zu. Was meldet der Compiler, was liefert Ihre Funktion?
Selbstkontrolle: Ihre Beobachtungen
  1. 0 1 2.
  2. AUS ist −1, ROT 0, GELB 1, GRUEN 2.
  3. GCC und Clang warnen: enumeration value 'GRUEN' not handled in switch [-Wswitch]. Das hilft, wenn später ein Wert dazukommt: Der Compiler zeigt jede Fallunterscheidung, die ihn noch nicht kennt. Die Warnung erscheint nur, wenn der switch keinen default hat.
  4. Der Compiler meldet nichts, und die Funktion landet in keinem case. Ein enum ist in C nur ein benanntes int; es dokumentiert, welche Werte gemeint sind, verhindert andere aber nicht.
Welche Aussagen zu typedef enum { FEHLER = -1, OK, VOLL } Ergebnis; stimmen?

Eine oder mehrere Antworten können richtig sein.

Erklärung anzeigen

Die erste und die vierte Aussage stimmen. Nach FEHLER = -1 zählt C weiter: 0, 1. Ein enum ist ein ganzzahliger Typ; andere Werte lassen sich zuweisen, ohne dass der Compiler einschreitet. Die Warnung für einen fehlenden case gibt es trotzdem.

4. Aufgabe: Ergebnisse als Aufzählung

Ersetzen Sie die #define-Konstanten für die Ergebnisse von inventar_aufnehmen durch einen eigenen Aufzählungstyp und verwenden Sie ihn als Rückgabetyp. Überall, wo das Ergebnis gespeichert oder unterschieden wird, soll dieser Typ stehen.

Hinweis: Negative Fehler

Die Fehler sollen negativ bleiben, denn so unterscheidet der übrige Code sie von Spielfällen. Ein Name in einem enum kann einen negativen Wert bekommen, und die folgenden zählen von dort weiter.

Bauen Sie danach den Vergleichslauf neu und prüfen Sie mit diff, dass sich nichts geändert hat.

Selbstkontrolle: Ihre Aufzählung
  • Die fünf #define-Zeilen sind verschwunden. An ihrer Stelle steht ein Typ, etwa Aufnahme, mit denselben fünf Namen.
  • Die Werte sind gleich geblieben: FEHLER_NAME −2, FEHLER_SPEICHER −1, AUFGENOMMEN 0, SCHON_VORHANDEN 1, INVENTAR_VOLL 2. Fängt die Aufzählung mit FEHLER_NAME = -2 an, ergeben sich die übrigen Werte von selbst.
  • Der neue Typ steht an zwei Stellen: als Rückgabetyp von inventar_aufnehmen und bei der Variablen in handeln, die das Ergebnis speichert. Der Kommentar über inventar_aufnehmen passt noch.
  • Die Abfragen in handeln brauchen keine Änderung: Ein Wert vom Typ Aufnahme lässt sich wie bisher mit < 0 und == vergleichen.
  • Das Programm übersetzt ohne Warnungen, und diff vorher.txt nachher.txt zeigt nichts.

Ihr Ergebnis: Eine Liste der Stellen, an denen Schlüssel und Tür vorkommen, die Datei vorher.txt und ein Aufzählungstyp für die Ergebnisse beim Aufnehmen, ohne dass sich das Verhalten geändert hat.
