Lernstandscheck I – Das Zahlenschloss

Sie entwickeln ein kleines Spiel für das Terminal. Vor Ihnen liegt ein Zahlenschloss mit einem dreistelligen Geheimcode. Sie haben insgesamt acht Versuche, um es zu öffnen. Sie können einen Code eingeben, einen Hinweis kaufen oder Ihren aktuellen Stand anzeigen lassen.

Lernziele

  • Variablen, Berechnungen, Bedingungen, Schleifen und Funktionen zu einem vollständigen Programm verbinden.
  • Eine Aufgabe in sinnvolle Teilaufgaben zerlegen und passende Schnittstellen festlegen.
  • Rückgabewerte verwenden und einen Fehlerwert beim Aufrufer überprüfen.
  • Das Programm mit selbst gewählten Fällen prüfen und Fehler systematisch eingrenzen.

Materialien

Startdatei, Makefile und Testdatei herunterladen. Entpacken Sie das gesamte Archiv und öffnen Sie tresor.c in Ihrer IDE. Alternativ können Sie im entpackten Ordner make und danach ./tresor ausführen. Nach Änderungen müssen Sie erneut übersetzen.

Die gesamte Umsetzung bleibt in einer C-Datei. Die Tastatureingaben mit scanf schreiben Sie selbst. Eigene Header, Arrays und zusätzliche Bibliotheken sind für Ihre Lösung nicht erforderlich.

Spielregeln

Der Geheimcode ist eine ganze Zahl von 100 bis 999. Er wird im Programm festgelegt und zu Beginn nicht ausgegeben. Ziffern dürfen mehrfach vorkommen. Verwenden Sie zunächst den vorgegebenen Geheimcode 427, damit die automatischen Tests funktionieren. Erst wenn diese Tests bestanden sind, dürfen Sie den Geheimcode nach Belieben innerhalb des gültigen Bereichs ändern. Für die bereitgestellten automatischen Tests stellen Sie ihn wieder auf 427. Die Spiellogik soll für jeden zulässigen Geheimcode funktionieren.

Das Menü bietet diese vier Möglichkeiten:

Auswahl Aktion Kosten
1 Einen Code eingeben Ein Versuch für einen gültigen Code
2 Einen Hinweis kaufen Ein Versuch bei jedem Aufruf
3 Den Status anzeigen Kein Versuch
0 Das Spiel beenden Kein Versuch

Code eingeben

Nach Auswahl 1 wird ein Code eingelesen. Zulässig sind Zahlen von 100 bis 999. Eine Zahl außerhalb dieses Bereichs wird mit einer Meldung abgewiesen. Sie verbraucht keinen Versuch und zählt nicht als gültige Codeeingabe.

Für einen gültigen Code verbrauchen Sie einen Versuch und geben aus, wie viele Ziffern an derselben Position mit dem Geheimcode übereinstimmen. Eine richtige Ziffer an einer anderen Position zählt nicht.

Beispiele bei Geheimcode 427:

Eingabe Rückmeldung
417 2 Ziffern an der richtigen Stelle
472 1 Ziffer an der richtigen Stelle
724 1 Ziffer an der richtigen Stelle
427 3 Ziffern an der richtigen Stelle – gewonnen

Einen Hinweis kaufen

Der Hinweis verrät die Summe der drei Ziffern des Geheimcodes. Bei 427 ist das 4 + 2 + 7 = 13. Jeder Aufruf kostet einen Versuch, auch wenn derselbe Hinweis schon einmal angezeigt wurde. Ein Hinweis zählt nicht als Codeeingabe.

Status anzeigen

Zeigen Sie die verbleibenden Versuche und die Anzahl der bisher gültigen Codeeingaben an. Zu Beginn sind das acht verbleibende Versuche und null gültige Codeeingaben. Hinweise und ungültige Eingaben erhöhen die Zahl der gültigen Codeeingaben nicht.

Spielende und ungültige Auswahl

  • Der exakt richtige Code öffnet das Schloss sofort. Das gilt auch beim letzten verbleibenden Versuch.
  • Sind alle Versuche verbraucht und wurde der Code nicht gefunden, bleibt das Schloss gesperrt und das Spiel endet.
  • Auswahl 0 beendet das Spiel unmittelbar mit einer passenden Meldung.
  • Andere ganzzahlige Menüauswahlen werden abgewiesen und verbrauchen keinen Versuch.
  • Nach einem Spielende werden keine weiteren Aktionen ausgeführt und das Menü erscheint nicht erneut.

Aufgaben

a) Das Programm planen

Notieren Sie sinnvolle Teilaufgaben. Halten Sie für Ihre geplanten Funktionen Aufgaben, Parameter mit Datentypen und Rückgabetypen fest. Überlegen Sie, welche Werte über mehrere Menüdurchläufe erhalten bleiben müssen und welche Größe konstant ist.

Planen Sie eine gemeinsame, selbst geschriebene Hilfsfunktion, die von mindestens zwei anderen selbst geschriebenen Funktionen für eine tatsächlich benötigte Teilaufgabe genutzt wird.

b) Funktionen implementieren

Setzen Sie Ihre geplanten Funktionen oberhalb von main um. Verwenden Sie Rückgabewerte für berechnete Ergebnisse. Mindestens eine selbst geschriebene Funktion soll eine ungültige Eingabe mit einem unterscheidbaren Fehlerwert zurückmelden. Der aufrufende Programmteil muss diesen Wert prüfen und den Fehler behandeln, bevor er mit dem Ergebnis weiterarbeitet.

Schreiben Sie außerdem mindestens eine eigene Ausgabefunktion mit Rückgabetyp void. Sie soll die ihr übergebenen Daten anzeigen. Sie müssen nicht jeden Ausgabebefehl in eine eigene Funktion verlagern.

c) Den vollständigen Spielablauf umsetzen

Verbinden Sie Menü, Eingaben, Funktionen und Spielzustand durch eine geeignete Schleife. Setzen Sie sämtliche Spielregeln um. Das Spiel soll nach einer normalen Aktion zum Menü zurückkehren, solange weder gewonnen noch abgebrochen wurde und noch Versuche vorhanden sind.

Die Gestaltung Ihres Menüs und zusätzliche verständliche Texte sind frei. Verwenden Sie für die geprüften Ergebnisse die Ausgabezeilen im folgenden Abschnitt, damit die automatischen Tests Ihre Ergebnisse erkennen können. Namen und Aufteilung Ihrer Funktionen wählen Sie selbst.

d) Eigene Testfälle durchführen und Fehler untersuchen

Wählen Sie mindestens sechs aussagekräftige Testfälle. Halten Sie jeweils Ausgangszustand, Eingaben, erwartetes und tatsächliches Ergebnis fest. Berücksichtigen Sie normale Abläufe, Grenzfälle und ungültige Eingaben.

Bei einer Abweichung können Sie vorübergehend Diagnoseausgaben ergänzen. Beschreiben Sie mindestens eine untersuchte Abweichung und die erneute Prüfung nach der Korrektur. Falls Sie keine Abweichung finden, dokumentieren Sie stattdessen eine gezielte Prüfung eines selbst gewählten Verdachts. Entfernen oder deaktivieren Sie anschließend die vorübergehenden Diagnoseausgaben. Reguläre Rückmeldungen über ungültige Eingaben bleiben erhalten.

Automatisch testen

Im Startmaterial liegen tresor.c, ein fertiges Makefile und test_tresor.py. Die Testdatei startet Ihr vollständiges Programm, spielt Eingabefolgen durch und prüft die Ausgaben. Sie müssen weder die Testdatei bearbeiten noch dafür bestimmte eigene Funktionsnamen verwenden.

Starten Sie nach Ihrer Umsetzung im Aufgabenordner:

make test

Dafür werden der C-Compiler, make und Python 3 benötigt. Alternativ können Sie Ihr Programm in der IDE übersetzen und im Terminal python3 test_tresor.py PFAD_ZUM_PROGRAMM ausführen. Verwenden Sie den Pfad zur ausführbaren Datei, nicht zur C-Quelldatei. Die Testdatei selbst wird nicht mit dem C-Compiler übersetzt.

Damit die Prüfung unabhängig von Ihrem Menü funktioniert, geben Sie diese Ergebniszeilen aus. N steht jeweils für die berechnete ganze Zahl und wird durch diese ersetzt:

Situation Ausgabe
Nach einer gültigen Codeeingabe Treffer: N
Beim Hinweis Hinweis: N
Beim Status, erste Zeile Versuche: N
Beim Status, zweite Zeile Tipps: N
Richtiger Code GEWONNEN
Alle Versuche ohne Sieg verbraucht GESPERRT
Abbruch mit Menüauswahl 0 BEENDET
Unzulässiger Code oder unbekannte Menüauswahl UNGUELTIG

Nach dem Schlüsselwort UNGUELTIG dürfen Sie eine zusätzliche Erklärung ergänzen. Nach einem richtigen Tipp geben Sie zunächst die Trefferzahl und anschließend die Gewinnmeldung aus. Beim Status erscheinen beide Zeilen. Drucken Sie keine Ergebnis-Schlüsselwörter vorsorglich in Ihrem Menü oder in Diagnoseausgaben ab.

Die Tests sind eine zusätzliche Kontrolle. Ihre eigenen begründeten Testfälle aus Aufgabe d bleiben Teil der Abgabe. Die leere Startdatei besteht die Tests noch nicht.

Eingaben prüfen

Lesen Sie Menüauswahl und geratenen Code mit scanf als ganze Zahlen vom Typ int ein. Prüfen Sie den Rückgabewert des scanf-Aufrufs: Beim Einlesen einer einzelnen Ganzzahl muss er 1 sein. Die 1 bedeutet, dass ein Wert erfolgreich eingelesen und gespeichert wurde.

Falls keine Zahl eingelesen wurde, geben Sie UNGUELTIG aus und beenden Sie das Programm mit return 1;.

Prüfen Sie bei einem eingelesenen Code außerdem den erlaubten Bereich 100 bis 999. Eine ganze Zahl außerhalb dieses Bereichs wird wie in den Spielregeln beschrieben abgewiesen und verbraucht keinen Versuch.

Abgabe und eigene Prüfung

Geben Sie Ihre tresor.c, Ihren Funktionsplan und Ihr Testprotokoll ab. Eine Textdatei oder ein lesbares Foto Ihres Plans genügt ebenfalls. Halten Sie kurz fest, welche Teile funktionieren und was gegebenenfalls noch offen ist.

Prüfen Sie vor der Abgabe:

  • Lässt sich die Datei neu übersetzen und starten?
  • Stimmen Verbrauch der Versuche und Anzahl gültiger Codeeingaben?
  • Werden berechnete Ergebnisse und Fehlerwerte unterschieden und geprüft?
  • Wird Ihre gemeinsame Hilfsfunktion an mindestens zwei sinnvollen Stellen verwendet?
  • Endet das Spiel bei Gewinn, gesperrtem Schloss oder Abbruch wie vorgesehen?
  • Sind Ihre Testfälle und Ergebnisse nachvollziehbar festgehalten?
