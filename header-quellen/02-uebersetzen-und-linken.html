Vom Quelltext zum ausführbaren Programm

Objektdateien erzeugen, die Arbeit des Linkers verfolgen, sie vom späteren Funktionsaufruf unterscheiden und Variablen über Dateigrenzen hinweg teilen.

1. Vom Quelltext zum Programm

Der Präprozessor verarbeitet die eingebundenen Header. Anschließend wird jede Quelldatei übersetzt. Dabei erzeugen Compiler und Assembler eine Objektdatei mit der Endung .o. Sie enthält bereits Maschinencode, Daten und Informationen für das spätere Verbinden.

Der Linker verbindet danach die Objektdateien und die benötigten Bibliotheken zum ausführbaren Programm rechner. Zu den Bibliotheken gehört immer die C-Standardbibliothek. Sie enthält zum Beispiel printf und liegt bereits übersetzt auf Ihrem System. Ein einzelner Aufruf wie gcc main.c calc.c -o rechner stößt alle diese Schritte nacheinander an.

2. Was der Linker verbindet

main.o enthält bereits übersetzten Code für den Aufruf von addiere. Wo der Code von addiere liegt, weiß main.o aber noch nicht, denn die Funktion steht in calc.o. Der Linker legt den Code aller Objektdateien zu einem Programm zusammen und trägt bei jedem Aufruf ein, wo die aufgerufene Funktion im fertigen Programm liegt.

Beim Ausführen springt der Ablauf bei einem Aufruf an diese Stelle und nach dem return zurück hinter den Aufruf. Die Aufteilung in Quelldateien spielt dann keine Rolle mehr: Das laufende Programm öffnet weder calc.c noch calc.o. Die Quelldateien dienen nur dazu, das Programm übersichtlich zu schreiben und zu bauen.

Die folgende Grafik zeigt, welche Verweise der Linker beim Rechner verbindet.

Die C-Standardbibliothek wird meist nicht ins Programm kopiert, sondern beim Programmstart vom Betriebssystem dazugeladen. Der Linker vermerkt dann im Programm, dass printf aus ihr stammt. Für Ihre eigenen Objektdateien gilt das nicht: Ihr Code steht vollständig in rechner.

Die erste und die vierte Aussage stimmen. Der Header wird schon beim Übersetzen gebraucht: Er macht die Signaturen bekannt. Zum Linken braucht es die Objektdateien mit dem übersetzten Code. Fehlt eine davon, meldet der Linker undefined reference to `addiere' (unter macOS Undefined symbols). Beim Ausführen werden keine Quelldateien mehr geöffnet.

3. Aufgabe: Übersetzen und Linken einzeln ausführen

Verwenden Sie Ihren aufgeteilten Rechner von Seite 1. Arbeiten Sie im Terminal in dessen Ordner.

  1. Übersetzen Sie die beiden Quelldateien einzeln. Prüfen Sie mit ls, welche Dateien neu entstanden sind. 
    gcc -std=c17 -Wall -Wextra -c main.c -o main.o
gcc -std=c17 -Wall -Wextra -c calc.c -o calc.o
    Mit -c endet der Aufruf, sobald die Objektdatei erzeugt ist. Es wird noch kein Programm gelinkt. -o benennt die jeweilige Ausgabedatei.
  2. Linken Sie die Objektdateien zum Programm und starten Sie es: 
    gcc main.o calc.o -o rechner
./rechner
  3. Versuchen Sie, nur mit main.o zu linken: gcc main.o -o rechner. Was meldet der Linker, und warum?
  4. Lassen Sie sich anzeigen, welche Art von Datei Sie vor sich haben. Unter Windows (MSYS2) heißt das Programm rechner.exe. 
    file main.c calc.h main.o rechner
  5. Sehen Sie sich die beiden Grafiken in Abschnitt 1 und 2 noch einmal an und ordnen Sie Ihre Befehle den Schritten zu. Erklären Sie, welche Schritte vor dem Programmstart stattfinden und was erst während der Ausführung passiert. Welche Aufgabe hatte calc.h, obwohl die Datei im Link-Befehl nicht vorkommt?
Hinweis: Der Befehl file fehlt

Unter Linux und macOS ist file vorhanden. Meldet MSYS2 unter Windows command not found, installieren Sie es einmal mit pacman -S file.

Hinweis: Beim Linken fehlt eine Funktion

Prüfen Sie, ob Sie beide Objektdateien angegeben haben. Der Header hat beim Übersetzen die Deklarationen bereitgestellt. Den übersetzten Code der Funktionen enthält aber nur calc.o.

Nur mit main.o meldet der Linker undefined reference to `addiere' (macOS: Undefined symbols): Der Aufruf kann mit keiner Funktion verbunden werden. Der Header wurde schon beim Übersetzen verarbeitet. Er hat die Signaturen bereitgestellt, mit denen der Compiler Aufrufe und Definitionen prüfen konnte. Zum Linken braucht es ihn nicht mehr. Erst beim Ausführen wird die Funktion tatsächlich aufgerufen.

Ihr Ergebnis: Sie können Quelltext, Objektdateien und Programm unterscheiden und erklären, welche Schritte zwischen ihnen liegen.

4. Text und Maschinencode

Alle Dateien bestehen aus Bytes. In einer Quelldatei stellen diese Bytes lesbaren Text dar. Eine Objektdatei und ein Programm enthalten dagegen Maschinenbefehle, Daten und Verwaltungsinformationen für Linker und Betriebssystem. file erkennt das an typischen Bytes am Dateianfang.

Öffnen Sie rechner testweise in einem Texteditor, versucht der Editor, diese Bytes als Text zu deuten. Es erscheinen ungewöhnliche Zeichen, nur einzelne Stücke wie Ihre Ausgabetexte bleiben lesbar. Wenn Sie das ausprobieren, schließen Sie die Datei ohne zu speichern, sonst ist das Programm danach beschädigt.

5. Variablen über Dateigrenzen: extern und static

Bisher teilen sich Ihre Quelldateien nur Funktionen. Auch eine globale Variable, also eine Variable außerhalb aller Funktionen, kann von mehreren Quelldateien verwendet werden. Dafür gilt dieselbe Unterscheidung wie bei Funktionen:

  • Die Definition legt die Variable an. Sie steht in genau einer Quelldatei, zum Beispiel in calc.c: int anzahl_rechnungen = 0;
  • Die Deklaration sagt nur: Diese Variable gibt es irgendwo im Programm. Dafür steht das Wort extern davor. Die Deklaration gehört in den Header, zum Beispiel in calc.h: extern int anzahl_rechnungen;

Jede Quelldatei, die calc.h einbindet, kann die Variable dann verwenden. Beim Übersetzen von main.c kennt der Compiler nur die Deklaration. Erst der Linker verbindet den Namen mit der einen Definition aus calc.o, genau wie bei einem Funktionsaufruf.

Ausprobieren

Arbeiten Sie in einer Kopie Ihres Rechner-Ordners, damit Ihre Lösung für die Aufgabe auf Seite 3 unverändert bleibt.

  1. Der Rechner soll zählen, wie viele Rechnungen er ausgeführt hat. Definieren Sie dafür in calc.c die Variable anzahl_rechnungen mit dem Anfangswert 0 und erhöhen Sie sie in addiere und multipliziere um eins. Deklarieren Sie die Variable mit extern in calc.h. Geben Sie ihren Wert am Ende von main aus.
  2. Verschieben Sie die Definition int anzahl_rechnungen = 0; aus calc.c in calc.h und ersetzen Sie damit die extern-Deklaration. Übersetzen Sie erneut. Welcher Schritt meldet einen Fehler, der Compiler oder der Linker? Warum hilft der Include-Schutz hier nicht?
  3. Stellen Sie den Zustand aus Schritt 1 wieder her und löschen Sie nur die Definition in calc.c. Was meldet der Linker jetzt?
Selbstkontrolle: Was Sie beobachten

Schritt 1 gibt zusätzlich Rechnungen: 2 aus.

In Schritt 2 übersetzt der Compiler beide Quelldateien ohne Fehler. Der Linker bricht ab, unter Linux mit multiple definition of `anzahl_rechnungen', unter macOS mit duplicate symbol. Beide Quelldateien binden den Header ein, also enthalten main.o und calc.o jeweils eine eigene Definition. Der Include-Schutz verhindert das nicht, denn er wirkt nur innerhalb der Übersetzung einer einzelnen Quelldatei.

In Schritt 3 meldet der Linker undefined reference to `anzahl_rechnungen' (macOS: Undefined symbols). Die Deklaration verspricht eine Variable, aber keine Objektdatei enthält ihre Definition. Das entspricht einer Funktion, die zwar im Header deklariert, aber nirgends definiert ist.

Merken Sie sich: In einen Header gehören Deklarationen, also extern-Variablen und Funktionsköpfe. Definitionen gehören in eine .c-Datei.

Das Gegenstück: static

Steht static vor einer globalen Variablen, ist sie nur in ihrer eigenen Quelldatei sichtbar. Der Linker verbindet sie mit keiner anderen Datei. Eine andere Quelldatei kann sie nicht verwenden, auch nicht mit einer extern-Deklaration. Zwei Quelldateien dürfen sogar jeweils eine eigene static-Variable mit demselben Namen haben, ohne dass sie sich stören. Dasselbe gilt für Funktionen: Eine static-Funktion ist eine Hilfsfunktion, die nur ihre eigene Datei verwendet. Ihre Deklaration gehört deshalb nicht in den Header.

Globale Variablen, die alle Quelldateien verändern können, machen Fehler schwer auffindbar: Ändert sich ein Wert unerwartet, kommt jede Datei als Ursache infrage. Verwenden Sie deshalb möglichst Parameter und Rückgabewerte. Braucht ein Programmteil einen Zustand, der während des ganzen Programmlaufs erhalten bleibt, legen Sie ihn als static-Variable in der Datei an, die für ihn zuständig ist. Andere Dateien erreichen ihn dann nur über die Funktionen dieser Datei. Im Kapitel „Pointer und Datenaustausch“ legen Sie so den Spielstand des Tresorraub-Spiels an. Mit extern teilen Sie eine Variable nur, wenn mehrere Dateien sie wirklich direkt brauchen.

Welche Aussagen stimmen?

Eine oder mehrere Antworten können richtig sein.

Erklärung anzeigen

Die zweite und die dritte Aussage stimmen. extern macht die Variable nur bekannt, angelegt wird sie durch die Definition in einer .c-Datei. Mit static ist sie nur in ihrer eigenen Datei sichtbar. Der Include-Schutz wirkt nur innerhalb der Übersetzung einer Quelldatei; bei einer Definition im Header enthält trotzdem jede Objektdatei eine eigene Definition, und der Linker bricht ab.
