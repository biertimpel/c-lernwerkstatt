Spielregeln aus einer Datei lesen

Zuglimit, Reichweiten der Wächter und Größe des Inventars stehen nicht mehr im Quelltext, sondern in regeln.txt.

1. Aufgabe: Spielregeln aus regeln.txt lesen

Bisher stehen die Spielregeln als Konstanten in tresorraub.c: ZUGLIMIT, INVENTAR_GROESSE und die Reichweiten der Wächter in startzustand. Wer mit anderen Regeln spielen will, muss den Quelltext ändern und neu übersetzen. Nach dieser Aufgabe genügt es, regeln.txt zu bearbeiten und das Programm neu zu starten.

Lesen Sie zuerst REGELN.md im Startmaterial. Dort stehen die vier Regeln, ihre Standardwerte und erlaubten Bereiche, das Format der Datei und das erwartete Verhalten. Gehen Sie dann in diesen Schritten vor:

  1. Die Regeln zusammenfassen. Legen Sie einen Typ an, der alle vier Regeln enthält, und eine Möglichkeit, ihn mit den Standardwerten zu füllen.
  2. Die Datei laden. Schreiben Sie eine Funktion, die regeln.txt Zeile für Zeile liest wie auf Seite 1 und jede Regelzeile zerlegt und prüft wie auf Seite 2. Beim ersten Fehler meldet sie Dateiname, Zeilennummer und Grund auf stderr und hört auf. Sie soll nur dann etwas ändern, wenn die ganze Datei fehlerfrei ist: Steht in Zeile 5 ein Fehler, darf auch der Wert aus Zeile 2 nicht übernommen werden.
  3. Die Regeln anwenden. Ersetzen Sie die Konstanten durch die geladenen Werte: das Zuglimit in der Statuszeile, die Reichweiten im Startzustand und die Größe des Inventars beim Aufnehmen. Danach sollte ZUGLIMIT nirgends mehr gebraucht werden. INVENTAR_GROESSE steckt auch im Laden eines Spielstands; dort bleibt das Dateiformat mit höchstens drei Inventarnamen bestehen, aber die Regel aus der Config kommt hinzu (Schritt 5).
  4. Die Regeln beim Start laden. Laden Sie die Datei in spiel_starten und zu Beginn von text_ausgeben. Bei einer fehlerhaften Datei liefern beide einen negativen Wert; das Programm endet dann, im Fenstermodus mit der Meldung Abbruch: spiel_starten hat einen Fehler gemeldet. Geben Sie in text_ausgeben die geltenden Regeln aus.
  5. Spielstände mit den Regeln laden. Ein Spielstand aus dem Kapitel „Datei-Ein- und -Ausgabe“ enthält keine Regeln. Beim Laden mit F9 gelten die Regeln des laufenden Spiels: Der Ladeversuch beginnt mit einem Startzustand nach diesen Regeln. Hat der Spielstand mehr Gegenstände im Inventar, als inventar_groesse erlaubt, bricht das Laden mit einer Meldung auf stderr ab, und der laufende Spielstand bleibt unverändert. So steht es in REGELN.md und FORMAT.md.
Hinweis: Alles oder nichts

Das Muster kennen Sie vom Laden eines Spielstands auf Seite 5 des Datei-Kapitels: erst in eine Kopie lesen, erst nach dem fehlerfreien Ende übernehmen. Die Regeln enthalten keine Pointer, deshalb genügt hier eine einfache Strukturzuweisung.

Hinweis: Wie kommen die Regeln an die Stellen, die sie brauchen?

Überlegen Sie, wer die Regeln während des Spiels kennen muss. Die Statuszeile und das Aufnehmen arbeiten mit dem Spielstand. Wenn der Spielstand seine Regeln selbst mitträgt, braucht keine Funktion eine zusätzliche globale Variable. startzustand kann die Regeln als Parameter bekommen.

Hinweis: Den gelesenen Namen einer Regel zuordnen

Für jede Regel braucht Ihr Programm ihren Namen, den kleinsten und den größten erlaubten Wert und das Feld, in das der Wert gehört. Zwei Wege führen zu übersichtlichem Code:

  • Ein if-Block mit strcmp je Regel. Damit sich die Prüfung des Werts nicht viermal wiederholt, steckt sie in einer gemeinsamen Hilfsfunktion, die die Grenzen als Parameter erhält.
  • Eine Tabelle: ein Array von Strukturen mit einem Eintrag je Regel, der alle Angaben zu dieser Regel bündelt. Eine Schleife sucht den Eintrag mit dem gelesenen Namen; findet sie keinen, ist die Regel unbekannt. Eine neue Regel braucht dann nur einen neuen Eintrag.

Vermeiden Sie mehrere Arrays, die nur über denselben Index zusammengehören: Nichts im Code stellt sicher, dass ihre Einträge zueinander passen. Bei der Tabelle bleibt die Frage, wie Ihr Code erfährt, in welches Feld der Wert gehört. Auch dass eine Regel schon einmal in der Datei stand, muss Ihr Programm sich je Regel merken, um „Regel steht doppelt“ zu erkennen.

Hinweis: Zwei Obergrenzen für das Inventar

Das Spielstandformat erlaubt höchstens drei Inventarnamen; daran ändert die Config nichts, und Ihre Ladefunktion braucht diese feste Grenze weiterhin, etwa für die Größe eines Arrays. Die Regel inventar_groesse kann kleiner sein. Geben Sie den beiden Grenzen verschiedene Namen, damit niemand sie verwechselt, und prüfen Sie beim Laden beide.

Hinweis: Zu lange Zeilen

Auf Seite 1 haben Sie gesehen, woran Sie eine Zeile erkennen, die nicht ganz in das Array gepasst hat. Planen Sie das Array so, dass eine Zeile mit 80 Zeichen samt '\n' und '\0' hineinpasst.

Welche Aussagen treffen auf Ihre fertige Lösung zu?

Eine oder mehrere Antworten können richtig sein.

Erklärung anzeigen

Die Regeln werden beim Start gelesen, in spiel_starten bzw. text_ausgeben. Spätere Änderungen wirken erst beim nächsten Start. Fehlende Regeln behalten ihren Standardwert. Bei einem Fehler gilt „alles oder nichts“: kein einziger Wert aus der Datei wird übernommen. Ein Spielstand, der mehr Gegenstände enthält, als die geltenden Regeln erlauben, wird beim Laden abgelehnt. Der Dateiname regeln.txt ist relativ; gesucht wird im Ordner, in dem das Programm gestartet wurde.

Ihr Ergebnis: Ein Spiel, dessen Regeln in regeln.txt stehen. Fehlende Angaben haben Standardwerte, fehlerhafte Dateien werden mit Zeile und Grund gemeldet, und gespeicherte Spielstände werden nur geladen, wenn sie zu den Regeln passen.

3. Ausblick

Ausblick: Eigene Level für Ihr Projekt

Am Ende des Kurses entwickeln Sie ein eigenes Projekt. Das kann auch eine Weiterentwicklung dieses Spiels sein. Eine lohnende Erweiterung sind verschiedene Level: Grundriss, Startposition und die Lage von Tür, Tresor, Gegenständen und Wächtern stehen dann nicht mehr im Quelltext, sondern werden aus Dateien gelesen, und das Spiel bietet mehrere Maps an.

Überlegen Sie dabei zum Beispiel: Wie lässt sich eine Map so in einer Textdatei beschreiben, dass ein Mensch sie lesen und bearbeiten kann? Woran erkennt Ihr Programm, dass eine Map nicht spielbar ist? Wie wechselt das Spiel zum nächsten Level, und was geschieht dabei mit Inventar und Zugzahl? Was muss ein gespeicherter Spielstand zusätzlich festhalten, damit er zur richtigen Map passt?
