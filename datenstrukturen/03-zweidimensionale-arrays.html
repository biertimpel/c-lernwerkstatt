Das Spielfeld als zweidimensionales Array

Ein Raster aus Zeilen und Spalten speichern, ausgeben und sicher abfragen.

1. Ein Raster aus Zeilen

Das Spielfeld des Tresorraubs ist 15 Felder breit und 9 Felder hoch. Der Grundriss aus SPIELFELD.md zeigt nur Wände (#) und freie Felder (.):

###############
#.....#.......#
#.##..#..###..#
#.............#
#.##..#.......#
#.....#.......#
#.....#.......#
#.....#.......#
###############

Ein zweidimensionales Array ist ein Array, dessen Elemente selbst Arrays sind. Bei int tabelle[3][4]; gibt es 3 Zeilen mit je 4 Elementen. Mit tabelle[1][2] greifen Sie auf Zeile 1, Spalte 2 zu. Auch hier beginnen beide Indizes bei 0.

Den Grundriss im Programm anlegen

Speichern Sie den Grundriss in einem zweidimensionalen char-Array. Jede Zeile des Grundrisses ist eine Zeichenkette, mit der Sie eine Zeile des Arrays initialisieren. Bestimmen Sie beide Größen selbst und begründen Sie sie in Ihrer Projektnotiz. Verwenden Sie für Breite und Höhe benannte Konstanten, wie unten unter „Benannte Konstanten für Breite und Höhe“ beschrieben.

Denkhilfe: Die zweite Dimension

Wie viele sichtbare Zeichen hat eine Zeile? Was steht nach Seite 2 am Ende jeder Zeichenkette zusätzlich? Wie viel Platz braucht eine Zeile also mindestens?

Benannte Konstanten für Breite und Höhe

Die Zahlen 15 und 9 brauchen Sie an vielen Stellen: bei der Deklaration des Arrays, in Schleifen und bei Bereichsprüfungen. Geben Sie ihnen deshalb Namen. Für Arraygrößen verwenden Sie dafür #define. Ein Beispiel, das nichts mit dem Spiel zu tun hat:

#define ANZAHL 3

int werte[ANZAHL] = {4, 8, 15};
for (int i = 0; i < ANZAHL; i++) {
    printf("%d\n", werte[i]);
}

#define ist wie #include eine Anweisung an den Präprozessor. Er bearbeitet den Quelltext, bevor der Compiler ihn übersetzt, und ersetzt dabei jedes Vorkommen von ANZAHL durch den Text 3. Der Compiler sieht also int werte[3]. Ändern Sie später die Größe, ändern Sie nur die eine Zeile mit #define.

Beachten Sie die Schreibweise: Zwischen Name und Wert steht kein Gleichheitszeichen, und am Ende steht kein Semikolon. Ein Semikolon würde an jeder Stelle mit eingesetzt und führt zu schwer verständlichen Fehlermeldungen. Namen für solche Konstanten schreibt man üblicherweise in Großbuchstaben.

Warum nicht const int?

Auf der Seite Funktionen haben Sie const kennengelernt: Eine so deklarierte Variable lässt sich nach dem Anlegen nicht mehr verändern. Für eine Arraygröße reicht das in C aber nicht. Damit ein Array mit Werten in geschweiften Klammern initialisiert werden kann, muss seine Größe schon beim Übersetzen feststehen. Eine const-Variable ist in C trotzdem eine Variable. Ihr Wert gilt beim Übersetzen nicht als feststehend.

Was dann passiert, hängt vom Compiler ab. GCC bricht mit einem Fehler ab, etwa „variable-sized object may not be initialized“. Clang, der Standardcompiler unter macOS, übersetzt das Programm und gibt nur eine Warnung aus, weil er hier eine eigene Erweiterung verwendet. Ihr Programm ließe sich dann nicht auf jedem System übersetzen. Mit #define vermeiden Sie das Problem.

Entwurfsfrage: Zeichen oder Zahlencodes?

Sie speichern den Grundriss als Zeichen: '#' für eine Wand, '.' für ein freies Feld. Genauso gut könnten Sie ein int-Array verwenden und jeden Feldzustand als Zahl codieren, zum Beispiel 0 für frei und 1 für Wand. Vergleichen Sie beide Darstellungen und halten Sie Ihre Überlegungen in der Projektnotiz fest:

  • Wie sieht die Initialisierung des Grundrisses jeweils im Quelltext aus? Welche ist leichter zu lesen und auf Tippfehler zu prüfen?
  • Was steht in den Daten, und was erscheint auf dem Bildschirm? Wo muss Ihr Programm zwischen beidem übersetzen?
  • Was müssten Sie ändern, wenn ein neuer Feldtyp hinzukommt, zum Beispiel Wasser?
Denkanstoß: Ein Zeichen ist auch ein Code

Auf der Seite Datentypen haben Sie gesehen, dass das Zeichen M im Speicher die Zahl 77 ist. Auch '#' ist also ein Zahlencode, nur einer, den man im Quelltext lesen kann. Bei Zahlen wie 0 und 1 muss man dagegen wissen, was sie bedeuten. Spätestens im Fenster brauchen Sie ohnehin eine Übersetzung: Dort zeichnen Sie für eine Wand ein Piktogramm, kein Zeichen. Es gibt hier keine allein richtige Antwort. Entscheidend ist, dass Sie Vor- und Nachteile benennen können.

2. Koordinaten und Zugriff

Wie beim SDL2-Fenster aus dem Kapitel „Manpages“ liegt (0, 0) links oben. Die x-Koordinate wächst nach rechts, die y-Koordinate nach unten. Eine Zeile des Arrays entspricht also einem festen y-Wert. Überlegen Sie, in welcher Reihenfolge Sie die beiden Indizes beim Zugriff auf das Feld (x, y) schreiben müssen. Prüfen Sie Ihre Antwort an einem Feld, bei dem Vertauschen ein anderes Zeichen liefert.

Den Grundriss auf zwei Arten ausgeben

  1. Geben Sie den Grundriss zeilenweise aus, also mit einer Ausgabe pro Zeile.
  2. Geben Sie ihn Feld für Feld mit zwei verschachtelten Schleifen aus. Welche Schleife läuft außen, welche innen? Achten Sie darauf, wie weit die Schleife über die Spalten läuft: Das Array hat eine Spalte mehr, als das Spielfeld Felder hat. Was ändert sich, wenn Sie die beiden Schleifen vertauschen?
  3. Zählen Sie die Wandfelder und die freien Felder. Notieren Sie vorher eine Schätzung.
  4. Zeichnen Sie den Grundriss im Fenster: Ersetzen Sie das Beispiel in zeichne durch zwei verschachtelte Schleifen, die für jedes Feld das Piktogramm für Wand oder Boden zeichnen. Wie berechnen Sie aus (x, y) die Pixelposition? Die README des Startmaterials hilft dabei. Geben Sie einen Fehler einer Zeichenfunktion sofort zurück, wie im Kapitel „Manpages“.
Selbstkontrolle: Ausgabe und Zählung

Beide Textausgaben müssen genau den Grundriss von oben ergeben. Im Fenster erscheint derselbe Grundriss aus Wand- und Bodenfeldern. Vertauschen Sie nur die beiden Schleifen und lassen den Zugriff unverändert, erscheint das Spielfeld gekippt: 15 Zeilen mit je 9 Zeichen. Der Grundriss hat 57 Wandfelder und 78 freie Felder, zusammen 135.

Gegeben ist char feld[9][16]; mit dem Grundriss als Inhalt. Welche Aussagen stimmen?

Eine oder mehrere Antworten können richtig sein.

Erklärung anzeigen

Die erste, dritte und vierte Aussage stimmen. Jede Zeile ist eine Zeichenkette mit 15 sichtbaren Zeichen. Das Nullzeichen steht danach in Spalte 15. Beim Vertauschen der Indizes erreichen Sie ein anderes Feld.

3. Aufgabe: Felder abfragen

Für die spätere Bewegung muss Ihr Programm zwei Fragen beantworten können:

  • Liegen die Koordinaten (x, y) innerhalb des Spielfelds?
  • Ist das Feld (x, y) begehbar? Begehbar ist ein Feld innerhalb des Spielfelds, das keine Wand ist.

Entwerfen Sie für beide Fragen eigene Funktionen und notieren Sie deren Verträge. Bei der zweiten Frage muss die Bereichsprüfung vor dem Zugriff auf das Array stehen. Begründen Sie in Ihrer Notiz, warum die Reihenfolge wichtig ist.

Prüfen Sie Ihre Funktionen mindestens mit diesen Koordinaten. Ergänzen Sie die erwarteten Ergebnisse, bevor Sie das Programm ausführen:

(x, y)Innerhalb?Begehbar?
(3, 7)
(0, 0)
(14, 8)
(15, 3)
(−1, 3)
(6, 3)

Ergänzen Sie eigene Fälle: Für jede der vier Seiten sollte mindestens ein Feld knapp außerhalb vorkommen und eines, das gerade noch innerhalb liegt.

Selbstkontrolle: Erwartete Ergebnisse

(3, 7) liegt innerhalb und ist begehbar. (0, 0) und (14, 8) liegen innerhalb, sind aber Wände. (15, 3) und (−1, 3) liegen außerhalb und sind deshalb nicht begehbar. (6, 3) ist im Grundriss ein freies Feld. Dort steht später die Tür, aber die gehört nicht zum Grundriss. Darum kümmern Sie sich auf Seite 5.

Ihre Funktion soll prüfen, ob (x, y) begehbar ist. Welche Aussagen stimmen?

Eine oder mehrere Antworten können richtig sein.

Erklärung anzeigen

Die erste und dritte Aussage stimmen. Schon der Zugriff mit einem ungültigen Index ist undefiniertes Verhalten, auch wenn Sie das Ergebnis nicht verwenden. Negative Koordinaten entstehen zum Beispiel, wenn die Figur am linken Rand nach links gehen will. Sie müssen deshalb genauso geprüft werden.
